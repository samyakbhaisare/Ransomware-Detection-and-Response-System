1. What You Are Building
You will build RDRS, a defensive program that watches a computer's files and processes and detects ransomware-like behavior as it happens. Ransomware encrypts a victim's files; encryption makes files look like random noise, and an attack changes many files very quickly and often renames them with strange new extensions. Your program watches for exactly those behaviors, scores how dangerous the activity is, and responds by alerting, logging, and saving evidence.
You build it in ten phases. Each phase produces something you can run and show before you move on. By the end you have a complete, tested, documented project for your portfolio.
Strictly defensive: You will never write, download, or run real ransomware or any malware. You test your detector with a small safe script that creates throwaway files in a dedicated sandbox folder (explained in Section 15). Never test on real personal files or on anyone else's computer.
2. Before You Start
You should be comfortable with basic Python (functions, classes, files) and using a terminal. You do not need prior security experience.
You need: Python 3.12 or newer, a code editor (such as VS Code), Git, and a terminal. Docker is only needed for the final phase.
3. Set Up Your Environment
Do this once at the very start. These commands create an isolated Python environment so your project's libraries stay separate from the rest of your computer.
python --version              # must be 3.12 or newer
mkdir rdrs && cd rdrs
python -m venv .venv
 
# Activate the environment:
source .venv/bin/activate     # macOS / Linux
.venv\Scripts\activate       # Windows (PowerShell)
 
# Core libraries you will use across the project:
pip install watchdog psutil pydantic pyyaml loguru sqlalchemy \
            fastapi uvicorn reportlab jinja2 pytest pytest-cov
Save the installed libraries so others can reproduce your setup:
pip freeze > requirements.txt

5. Phase 1: Project Setup & Entropy Detector
Goal: Create the foundation files and the entropy function that the whole system relies on.
Tasks:
Write a small config loader that reads settings from config.yaml: which folders to watch, and the alert thresholds.
Set up rotating log files (one each for system, events, alerts, errors, and audit). The loguru library makes this easy.
Implement Shannon entropy: a function that takes bytes and returns a number from 0 (totally predictable) to 8 (totally random).
Add a helper that reads the first 64 KB of a file and returns its entropy (sampling keeps it fast on big files).
Commands / hints:
# Entropy idea (pseudocode):
#   count how often each byte value appears
#   for each count: p = count / total;  entropy -= p * log2(p)
#   return entropy   (0.0 .. 8.0)
Done when: A normal text file returns a low entropy (about 0–5), and a file full of random bytes returns close to 8.0.
6. Phase 2: Real-Time File Monitoring
Goal: Watch folders and react the instant a file changes.
Tasks:
Use the watchdog library to watch the folders listed in config.yaml.
Capture four kinds of change with their timestamps: create, modify, rename/move, and delete.
Turn each raw event into your own small object holding: event type, file path, time, and file extension.
Print a running count of events so you can see the monitor working live.
Commands / hints:
python -m app.main --watch ./data
# In a second terminal, create and rename files in ./data and watch the count rise.
Done when: Creating, renaming, or deleting files in a watched folder updates your live event count.
7. Phase 3: Database & Process Monitoring
Goal: Store everything you observe, and find out which program is responsible.
Tasks:
Use SQLAlchemy with SQLite to create tables for events, processes, scores, alerts, and incidents.
Use the psutil library to take snapshots of running processes: name, CPU %, memory, disk writes, executable path, and parent process.
Save file events and process snapshots into the database as they happen.
Commands / hints:
# SQLite needs no server — it is just a file at data/rdrs.db
# Handle 'access denied' from psutil gracefully; some system processes are protected.
Done when: After running the monitor, your database contains rows for file events and process snapshots.
8. Phase 4: Detection Engine
Goal: Turn a stream of single events into meaningful signals over a time window.
Tasks:
Keep a sliding window of recent events (for example, the last 60 seconds).
Whenever a new event arrives, recompute: files modified per minute, number of renames, number of extension changes (such as .docx becoming .locked), and the average entropy of newly written files.
Compare these against the thresholds in config.yaml to decide when a dangerous “burst” is happening.
Done when: A rapid burst of file changes pushes these counters above their thresholds, while normal activity stays below them.
9. Phase 5: Threat Scoring & Incident Response
Goal: Combine the signals into a single 0–100 score using simple, transparent rules — then respond. (No datasets or training needed; the scoring is plain weighted rules you control.)
Tasks:
Give each signal a weight (all configurable): rapid encryption 40, mass rename 30, high entropy 25, CPU spike 15, unknown program 10. Add the weights of the signals that fired and cap the total at 100.
Map the score to a level: Normal (0–40), Warning (40–70), Critical (70–100).
On Critical: create an incident record, save the list of affected files and the suspect process, and write to the alert and audit logs.
Copy the evidence files into a quarantine folder — copy only, never change or delete the originals.
Keep simulation mode ON by default: if process termination is switched on, only LOG what it would do; do not actually kill anything.
Why rules instead of AI here: a weighted rule engine is transparent (you can explain every point of the score), it needs no training data at all, and it is the right level for a first project. 
Done when: A simulated burst produces a Critical score, an incident record, an alert-log entry, and copied evidence — with the original files untouched.
10. Phase 6: REST API
Goal: Expose the system's state over HTTP so other tools (and your dashboard) can read it.
Tasks:
Use FastAPI to add endpoints: GET /health, /status, /alerts, /events, /reports; POST /scan and /settings.
Return JSON from every endpoint.
Use FastAPI's automatic documentation page to test your endpoints.
Commands / hints:
uvicorn app.api.main:app --reload
# Then open http://127.0.0.1:8000/docs in your browser.
Done when: You can call /status and /alerts in the browser and get JSON responses back.
11. Phase 7: Dashboard
Goal: Build a simple security-operations dashboard so a person can see what is happening.
Tasks:
Make a web page (plain HTML + Bootstrap + JavaScript is perfectly fine; React is optional) showing: current threat level, recent alerts, recent events, top modified files, and a CPU / entropy chart.
Fetch fresh data from your API every few seconds so the page updates by itself.
Use a dark theme for a clean operations look.
Done when: Opening the dashboard shows live status that updates on its own while the monitor runs.
12. Phase 8: Reporting
Goal: Produce a clear report of an incident that someone could read or file.
Tasks:
Generate an incident report in JSON and CSV (required). Add HTML and PDF (using reportlab) if you have time.
Include: a timeline of events, the threat score, the list of affected files, the suspect process, and recommendations.
Commands / hints:
# JSON and CSV use Python's built-in json and csv modules — no extra setup.
# PDF: use reportlab;  HTML: use a jinja2 template.
Done when: After an incident you can generate at least a JSON report and a CSV report file.
13. Phase 9: Testing
Goal: Prove your code works and keep it working as you change it.
Tasks:
Write unit tests for the entropy function and the scoring engine (these are pure logic and easy to test).
Write one integration test that feeds a burst of fake events through the pipeline and checks that a Critical incident is produced.
Measure how much of your code the tests cover; aim for 90% or more.
Commands / hints:
pytest --cov=app
Done when: Your tests pass and the coverage report shows a high percentage.

15. How to Safely Test Your Detector
You must never use real ransomware. Instead, use this tiny safe script to trigger your detector. It works only inside a dedicated sandbox folder: it creates brand-new throwaway files, fills them with random bytes (so they look encrypted), and renames them with a .locked extension. It never touches your real files, never spreads, and deletes nothing of yours. This is a test trigger, not a dataset and not malware — the same idea as the harmless test file used to check antivirus software.
import os, pathlib
sandbox = pathlib.Path('data/sandbox'); sandbox.mkdir(parents=True, exist_ok=True)
 
# 1) create 50 normal files
for i in range(50):
    (sandbox / f'file_{i}.txt').write_text('normal document content')
 
# 2) simulate an attack: overwrite with random bytes + rename
for f in list(sandbox.glob('*.txt')):
    f.write_bytes(os.urandom(20000))        # high-entropy, looks encrypted
    f.rename(f.with_suffix('.locked'))      # mass extension change
Run your monitor on the data/sandbox folder, then run this script in another terminal. Your detector should detect the burst, reach a Critical score, and create an incident with copied evidence — while leaving everything outside the sandbox alone.

18. Rules & Responsible Use
This is a detection tool only. Never write, download, or run real ransomware or any malware.
Test only with the sandbox self-test in Section 15 — never on real user files or another person's computer.
Keep automated response in simulation mode; never build code that kills processes on a shared machine.
Do your own work and credit any libraries or sample code you use.
Keep passwords and keys out of your repository — use environment variables.

Final tip: a smaller, clean, well-tested and well-documented submission scores better than a large half-finished one. Build each phase until its “Done when” check passes, then move on.
